# دمج Aram AI داخل TermiAI-Nexus

- تم استخراج `ModelRuntime` و`ApiHttpServer` و`ApiKeyStore` و`ModelFiles` و`AppPrefs` من Aram AI إلى Android Library باسم `:aram-engine`.
- يستدعي Flutter المحرك عبر `MethodChannel` داخل عملية Android نفسها. لا يعتمد الاتصال الداخلي على HTTP إلى `127.0.0.1`، وهو المسار الذي واجه مهلة انتظار سابقًا.
- يبقى دعم بوابات OpenAI-compatible الخارجية محفوظًا عندما يكون العنوان غير محلي. العنوان الفارغ أو loopback يوجّه إلى المحرك المضمّن.
- يشغّل المحرك خدمة Android أمامية، وينزّل GGUF إلى مساحة TermiAI-Nexus الخاصة عند عدم وجوده، مع منع التنزيل عبر بيانات الهاتف المقاسة افتراضيًا. بيانات التطبيقين منفصلة؛ لذلك لا يستطيع TermiAI قراءة نسخة النموذج داخل مساحة Aram AI الخاصة تلقائيًا، وقد يلزم تنزيل نسخة ثانية تقارب 1.65 GB.
- API المضمّن يستمع محليًا على `127.0.0.1:8766` لتجنّب التصادم مع خادم Aram AI المستقل على `8765`. الوضع الافتراضي لا يفتح المنفذ على الشبكة المحلية.
- واجهة MethodChannel وملف Dart `AramEngineBridge` يوفّران إنشاء مفتاح مالك، وإنشاء مفاتيح عملاء بحصص يومية، وعرض بياناتها، وإلغاءها. لا تُعاد الأسرار إلا لحظة الإنشاء. شاشة إدارة المفاتيح المرئية في Flutter ليست ضمن هذا التغيير بعد؛ طبقة الاستدعاء جاهزة لربطها.
- حد Android الأدنى يصبح API 33 لأن مكتبة llama.cpp المثبتة في Aram AI تطلب `minSdk 33`. هذا يناسب أجهزة Android 13 فأحدث، لكنه يستبعد Android 12 وما قبله.
- يبقى تطبيق Aram AI المستقل دون تعديل. نواة المصدر المثبتة هي commit `e68bd5c1b279c6a41daf96a5a30b9e9a4a5b0a85`.

## التحقق

يفحص GitHub Actions إعدادات SDK/NDK/CMake ويهيئ مصدر llama.cpp المثبت ثم يبني APK Debug ويرفعه كـ artifact. لا يعتبر الدمج ناجحًا نهائيًا قبل نجاح Workflow وتثبيت APK واختبار التوليد الحقيقي على الهاتف.
