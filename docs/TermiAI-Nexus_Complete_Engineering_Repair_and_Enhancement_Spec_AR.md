## 1. الغرض ونطاق الوثيقة

تجمع هذه الوثيقة في مرجع واحد:

1. نتائج المراجعة الفعلية للفرع الرسمي من المستودع.
2. تشخيص مشكلة تأخر خطة العمل واختفاء نتيجتها في محادثة المساعد.
3. تشخيص مشكلة تثبيت Ubuntu وأدوات Linux وفقدان تقدم التثبيت.
4. شاشة الترحيب والتهيئة الإلزامية الموحدة لمحرك Aram AI وUbuntu وأدوات Linux.
5. ربط GitHub عبر GitHub App مع حصر الوصول بالمستودعات التي يحددها المستخدم.
6. مواصفات TermiAI-Nexus المعتمدة سابقًا، بما فيها الوكلاء المحليون والعالم الافتراضي ثلاثي الأبعاد وسير تنفيذ المشاريع والتعافي الآمن.
7. ترتيب التنفيذ ومعايير القبول والاختبارات التي تمنع تكرار المشكلات.

**حدود مهمة:** لا يمكن تنفيذ التغييرات المطلوبة بصورة صحيحة في ملف Dart أو Kotlin واحد؛ فهي تمس واجهات Flutter، والتخزين الدائم، وقنوات Android الأصلية، وخدمات الخلفية، والتفويض الأمني مع GitHub، والاختبارات. لذلك هذه الوثيقة هي عقد التنفيذ الكامل الذي يحدد ما ينبغي تغييره وكيفية إثبات نجاحه. لم تُعدّل ملفات المستودع ولم يُنشأ commit أو push أثناء إعدادها.

## 3. تشخيص مشكلة محادثة المساعد وخطة العمل

### 3.1 مسار التنفيذ الموجود حاليًا

المسار الفعلي الذي تمت مراجعته:

1. `lib/screens/assistant_screen.dart` — الدالة `_submit()` تستقبل النص، وتحفظ رسالة المستخدم، ثم تستدعي `AiGateway.chat()` لتصنيف الرسالة إلى محادثة عادية أو طلب مشروع.
2. إذا كان الطلب مشروعًا، تستدعي الشاشة `ProjectCoordinator.prepare(projectRequest)`.
3. `lib/core/project_coordinator.dart` — تنشئ `prepare()` معرّفًا ومساحة عمل، ثم تستدعي `AiGateway.createPlan()`، ولا تنشئ `ProjectRecord` ولا تحفظه في `ProjectJobStore` إلا بعد عودة الخطة.
4. `lib/core/ai_gateway.dart` — `createPlan()` يطلب من النموذج خطة من 3 إلى 8 مهام، ويعيد الطلب مرة واحدة إذا كان JSON غير صالح.
5. `android/app/src/main/kotlin/com/aram/termaix/AramEngineChannel.kt` — عند استدعاء `generate`، يبدأ تشغيل خدمة المحرك عند الحاجة ثم ينتظر جاهزية النموذج قبل إرسال الطلب إلى `ModelRuntime.generate()`.
6. `android/aram-engine/src/main/java/com/aram/ai/engine/ModelRuntime.kt` — التوليد يمر عبر طابور أولوية متسلسل، وتُنفذ الاستدلالات على محرك محلي واحد.

إذًا طلب المشروع قد يستهلك استدلالًا أوليًا للتصنيف، واستدلالًا ثانيًا لتوليد الخطة، وقد يستهلك استدلالًا ثالثًا عند إعادة تنسيق الخطة غير الصالحة.

### 3.2 السبب المؤكد لاختفاء النتيجة بعد مغادرة الشاشة

في `lib/app_shell.dart` تُنشأ الصفحة المختارة من جديد عبر `_page()` و`KeyedSubtree(key: ValueKey(_selected), ...)`. عند تغيير الصفحة، يمكن التخلص من `AssistantScreen` وإعادة إنشائها.

في `_submit()` داخل `assistant_screen.dart`، بعد انتهاء `prepare()` يوجد شرط:

```dart
if (!mounted) return;
```

ثم فقط بعد هذا الشرط تُضاف الخطة إلى رسائل المحادثة وتُحفظ. إذا انتهى التوليد بعد التخلص من الشاشة، فلن تُضاف النتيجة إلى سجل المحادثة. وعند العودة، تستعيد الشاشة الرسائل المحفوظة فقط؛ ولا توجد مهمة تخطيط مستقلة محفوظة يمكنها إعادة ربط الطلب بنتيجته.

كذلك، لا ينشئ `ProjectCoordinator.prepare()` سجل المشروع إلا بعد نجاح التوليد. لذلك لا يوجد `ProjectRecord` دائم خلال فترة انتظار الخطة، وقد تبقى مساحة عمل أُنشئت قبل استجابة النموذج دون سجل مهمة مكتمل.

**هذا تفسير مباشر ومدعوم بالكود لحالة انتهاء العمل دون ظهور الخطة بعد الخروج والعودة.**

### 3.3 أسباب التأخير وعدم وضوحه

- استدعاء المحرك المحلي عبر MethodChannel في `AiGateway.chat()` لا يملك مهلة Dart صريحة مماثلة لمهلة HTTP.
- `AramEngineChannel.generate` ينتظر تحميل النموذج حتى 900 محاولة بفاصل 500ms؛ أي حد انتظار يصل إلى 450 ثانية عند الحاجة إلى تحميل النموذج.
- `ModelRuntime` يمرر الطلبات في طابور متسلسل. لا يمكن بدء استدلال ثانٍ على النموذج نفسه بالتوازي مع الاستدلال النشط.
- `AramEngineChannel` يستدعي `ModelRuntime.generate(...){ }` مع callback فارغ؛ فلا تصل الرموز المولدة تدريجيًا إلى واجهة Flutter.
- لا يرسل المساعد للمستخدم اسم المرحلة الحالية، ولا وقت الانتظار، ولا حالة الطابور، ولا سبب التأخير.
- لا يمرر `_submit()` معرف طلب ثابتًا معروفًا إلى `chat()`، رغم وجود مسار إلغاء `cancelGeneration` في الجسر.

لا يمكن الجزم بسبب تأخر طلب بعينه دون سجل وقت التنفيذ وحالة المحرك والطابور في لحظة الطلب. قد يكون السبب تهيئة باردة للنموذج، أو انتظار طلب سابق في الطابور، أو استدلالًا بطيئًا، أو تعطلًا. لا يجوز عرض أحد هذه الاحتمالات كحقيقة من دون دليل.

### 3.4 الإصلاح المطلوب — خدمة تخطيط دائمة

يُنقل مالك عملية التخطيط من عمر Widget إلى خدمة/منسق على مستوى التطبيق وخدمة Android مناسبة للمهام طويلة المدة. يجب أن يصبح الطلب مهمة دائمة مستقلة عن شاشة المحادثة.

#### نموذج حالة مهمة التخطيط

كل طلب يحصل على `planningJobId` ثابت قبل بدء أي استدلال، ويتضمن على الأقل:

- `planningJobId` و`conversationId` و`projectId` عند توفره.
- نص المستخدم والسياق اللازم، مع مرجع مرفق الصورة عند الحاجة، لا نسخ غير ضرورية للبيانات الكبيرة.
- وقت الإنشاء وآخر تحديث ووقت بدء وانتهاء كل مرحلة.
- حالة المهمة: `queued`, `classifying`, `planning`, `validating`, `ready_for_approval`, `failed`, `cancel_requested`, `cancelled`, `interrupted`, `recoverable`.
- `requestId` لكل استدلال محلي قابل للإلغاء.
- استجابة النموذج الخام عند الحاجة للتشخيص، مع حدود حجم واضحة وعدم تسجيل أسرار.
- الخطة المحللة أو `projectId` أو الخطأ المصنف.
- عدد محاولات إصلاح تنسيق الخطة وسبب كل محاولة.

تُحفظ المهمة فور إرسالها وقبل الاتصال بالنموذج. يجب ألا تعتمد استعادة الطلب على وجود Widget أو `BuildContext`.

#### المراحل المرئية للمستخدم

1. استلام الطلب وحفظه.
2. فهم الطلب وتصنيفه.
3. بناء خطة العمل.
4. التحقق من بنية الخطة وتوزيع المهام.
5. أصبحت الخطة جاهزة للمراجعة.
6. فشل مع توضيح السبب أو تعذر الاستئناف.

يُعرض زمن المرحلة الفعلي وحالة الانتظار عند توفرها. يمكن إظهار الرموز تدريجيًا فقط بعد توصيل تدفق `onToken` الحقيقي من `ModelRuntime` إلى EventChannel أو آلية بث موثوقة. لا تُعرض نسبة مئوية لتوليد النص ما لم يوجد قياس حقيقي صالح.

#### شروط الحفظ والتعافي

- حفظ رسالة المستخدم ومعرف مهمة التخطيط قبل تنفيذ أول استدلال، وانتظار اكتمال الكتابة الحرجة بدل تركها غير منتظرة.
- حفظ كل انتقال حالة مهم إلى تخزين دائم موثوق.
- عند الانتقال بين الشاشات، تظل الخدمة مستمرة، وتعرض الشاشة الجديدة الحالة نفسها.
- عند إعادة تشغيل التطبيق، تستعيد الشاشة المهمة من `planningJobId` وتعرض النتيجة التي حُفظت حتى لو كانت الشاشة القديمة قد اختفت.
- عدم إنشاء مشروع أو مساحة عمل مكررة عند تكرار callback أو إعادة فتح التطبيق.
- استخدام مفتاح idempotency أو معرف ثابت للطلب؛ لا يكفي UUID جديد في كل retry.
- لا تُعرض الخطة قبل التحقق من JSON والمهام والأدوار والتسلسل.
- لا يبدأ أي وكيل بتنفيذ المهام قبل موافقة المستخدم على الخطة.
- يجب ألا يوقف timeout قصير استدلالًا بطيئًا مشروعًا. تُضبط حدود زمنية منفصلة لتحميل النموذج، وانتظار الطابور، والاستدلال، وإعادة تنسيق JSON، مع إلغاء حقيقي وتسجيل السبب.
- عند قتل العملية أو فقد الجهاز للطاقة، تُصنف المهمة `interrupted` أو `recoverable` مع تمييز مرحلة التوقف. لا يُعاد الاستدلال تلقائيًا بطريقة قد تنشئ مشروعًا مكررًا.
- بعد نجاح الخطة، تُربط النتيجة بالمحادثة وبسجل المشروع الدائم قبل عرضها.

#### خيارات تقليل عدد الاستدلالات

يُقاس أولًا زمن التصنيف والخطة كل على حدة. يمكن دراسة دمج التصنيف والخطة في استجابة منظمة واحدة لتقليل زمن الانتظار، بشرط أن تجتاز اختبارات دقة فصل المحادثة العادية عن طلبات المشاريع، وألا يتجاوز ذلك حد النموذج أو يؤدي إلى خطط ناقصة. لا يُنفذ الدمج لمجرد تقليل عدد الاستدعاءات دون اختبار.

## 4. تشخيص تثبيت Ubuntu وأدوات Linux

### 4.1 الوضع الحالي في الكود

- `lib/core/linux_runtime_service.dart` يوفر `isInstalled()` و`install()` وStream للأحداث.
- `lib/screens/terminal_screen.dart` يملك حالة التثبيت داخل Widget ويشترك في `installEvents` أثناء التثبيت.
- `LinuxRuntimeChannel.kt` يستخدم `AtomicBoolean installing` لمنع بدء تثبيت ثانٍ.
- عند `onListen` يحفظ EventSink الحالي فقط، ولا يرسل آخر Snapshot.
- عند `onCancel` يزيل EventSink؛ وبذلك لا تتلقى الشاشة الجديدة الأحداث التي فاتتها.
- تشغيل التثبيت يتم عبر خيط `daemon` باسم `termai-linux-install`، وليس عبر خدمة Android مستقلة ذات حالة دائمة.
- عند تكرار طلب التثبيت أثناء وجود عملية، يعيد الكود `LINUX_INSTALL_BUSY` بدل إرجاع حالة العملية الجارية.
- `TerminalScreen.dispose()` يلغي اشتراك الأحداث، ويفقد Widget حالة التقدم المحلية.
- مرحلة `packages` ترسل حدثًا واحدًا قبل تنفيذ أمر `apt-get`؛ ولا يوجد تقدم تفصيلي لكل حزمة.
- `downloadAndVerify()` يحذف ملف `.part` السابق قبل بدء التنزيل، ويحذف الملف الجزئي عند الخطأ؛ لا توجد آلية استئناف تنزيل Range في المسار الحالي.
- التحقق النهائي الحالي جيد ويجب الحفاظ عليه: اختبار Bash داخل PRoot، وفحص Ubuntu، والتحقق من Git وGitHub CLI وPython، ثم كتابة علامة التثبيت بعد النجاح.
- عند فشل التثبيت، قد يُحذف rootfs غير المعلم باعتباره تثبيتًا غير مكتمل. يجب تحسين التعرف على ملكية ملفات العمل الجزئية قبل اعتماد آلية التعافي، وعدم حذف بيانات غير معروفة أو ملفات مستخدم دون تحقق.

### 4.2 معنى الخطأ `LINUX_INSTALL_BUSY`

هذا الخطأ يعني أن القفل `installing` كان ممسوكًا عند وصول الطلب الثاني. **لا يثبت وحده أن التثبيت عالق أو متوقف أو يتقدم.** يجب أن يستعلم التطبيق عن حالة العملية الحالية، وتاريخ آخر تقدم، ومرحلتها، وآخر heartbeat، ثم يقرر إن كانت نشطة أو متوقفة أو تحتاج إلى تعافٍ.

### 4.3 الإصلاح المطلوب — مدير تثبيت مركزي ودائم

تُنقل ملكية حالة التثبيت من الشاشة إلى مدير عملية دائم في طبقة Android مع واجهة Dart موحدة.

#### API مطلوبة

- `getInstallStatus`: يعيد Snapshot كاملًا للحالة الحالية.
- `startOrJoinInstall`: يبدأ التثبيت إن لم توجد عملية، أو يعيد حالة العملية الحالية إذا كانت جارية؛ لا يعيد `LINUX_INSTALL_BUSY` كحالة عادية للمستخدم.
- `cancelInstall`: يرسل إلغاءً آمنًا إذا كانت المرحلة قابلة للإلغاء، مع حفظ الحالة.
- EventChannel يعيد Snapshot فور الاشتراك، ثم يرسل التحديثات اللاحقة.
- `isInstalled` يبقى فحص جاهزية نهائيًا، ولا يُستبدل بمجرد فحص وجود مجلد أو اكتمال تنزيل.

#### بيانات الحالة الدائمة

يُحفظ على الأقل:

- `installId`, `state`, `stage`, `message`, `startedAt`, `updatedAt`, `heartbeatAt`.
- `downloadedBytes`, `totalBytes`, `remainingBytes`, `percent` عندما تكون المقاييس حقيقية.
- `currentPackage`, `completedPackages`, `failedPackage` إذا أمكن استخراجها من بيانات apt/dpkg الفعلية.
- `errorCode`, `errorMessage`, `retryable`, `rootfsPath`, `archivePath`.
- حالة `interrupted` بعد موت العملية أو الجهاز، بدل ترك قفل قديم أو ادعاء أن التثبيت ما زال يعمل.

#### الاستمرار في الخلفية

لا يكفي خيط `daemon` لضمان بقاء العملية إذا قتل Android عملية التطبيق. يجب تنفيذ عملية التهيئة داخل خدمة Android ملائمة، مع إشعار foreground واضح، وسياسة lifecycle واستعادة.

يُختار نوع الخلفية وفق طبيعة العملية وإصدار Android المستهدف وسياساته الحالية:

- تنزيل ملف المستخدم بدأه صراحةً: يُدرس User-Initiated Data Transfer Job أو واجهة Android مخصصة للتنزيل حيث تكون أنسب.
- فك الضغط وتهيئة النظام وتثبيت الحزم: يُدرس Foreground Service بنوع مسموح ومعلن، أو WorkManager طويل المدة حيث يناسب العمل، مع مراعاة حصص Android 16 وقيود الخدمات الأمامية.
- لا يُضاف `specialUse` أو نوع خدمة آخر دون التأكد من شروط Android ومتطلبات توزيع التطبيق.

يجب أن يظل التطبيق قادرًا على عرض آخر حالة حتى لو أُعيد إنشاء FlutterEngine أو Widget. لا يُفترض أن إعادة تشغيل التطبيق تعني أن التثبيت ما زال يعمل؛ تُفحص العملية الفعلية وملفاتها ويُصنف الوضع بدقة.

#### تقدم أدوات Linux

يجب فصل التقدم إلى مراحل فعلية:

1. تنزيل Ubuntu: bytes وtotal وremaining وpercent من النقل الحقيقي.
2. التحقق من SHA-256 للملف.
3. استخراج rootfs.
4. التحقق من نظام Ubuntu وملفات Bash وELF loader.
5. إعداد PRoot والـ mounts.
6. تثبيت أدوات Linux.
7. فحص نهائي وتشغيل أوامر smoke test.

مرحلة الحزم لا تُعرض ككتلة صامتة. تُستخرج حالة الحزم من معلومات `apt/dpkg` الفعلية (مثل status events أو بيانات التثبيت القابلة للتحليل)، مع عرض اسم الحزمة التي يجري تجهيزها والحزم المكتملة والفاشلة. لا تُحسب نسبة مئوية إلا إذا كان إجمالي العمل معلومًا وقياسه موثوقًا؛ وإلا يظهر اسم المرحلة والحزمة دون نسبة.

#### الاستئناف وحماية الملفات

- استخدام ملف جزئي مع تحقق من `ETag`/`Content-Range` عندما يدعم المصدر الاستئناف، وعدم افتراض أن كل مصدر يدعمه.
- إذا لم يدعم المصدر الاستئناف، تظهر رسالة أن إعادة التنزيل مطلوبة ولا يُدّعى الحفاظ على التقدم.
- تنزيل الملف إلى ملف مؤقت، ثم التحقق منه، ثم ترقيته ذريًا إلى الملف المعتمد.
- إنشاء `installId` وعلامة ملكية واضحة لملفات rootfs التي أنشأتها هذه المهمة.
- فصل rootfs الجزئي عن rootfs المعتمد، وعدم استبدال نسخة سليمة قبل نجاح النسخة الجديدة.
- عدم حذف مجلد Linux غير معروف أو يحتوي بيانات مستخدم دون فحص الملكية وأخذ نسخة/لقطة قابلة للاستعادة.
- بعد تعطل التثبيت، تُحدد مرحلة الاستعادة: استكمال آمن، أو إعادة مرحلة محددة، أو عرض إصلاح يتطلب موافقة. لا يُعاد تنفيذ `apt-get` عشوائيًا إذا كانت حالته غير معروفة.

## 5. شاشة الترحيب والتهيئة الأولية الإلزامية

### 5.1 تجربة الدخول المعتمدة

تكون أول واجهة بعد تشغيل التطبيق شاشة ترحيب أنيقة واحترافية، وتعرض النصين التاليين كما اعتمدهما المستخدم:

**العنوان:** «مرحبًا بك في Termi Ai Nexus»

**التوضيح:** «لإكمال الدخول للخدمة المجانية يجب عليك تثبيت بعض الأدوات لضمان عمل التطبيق بشكل ناجح وبدون أخطاء»

**الزر الأساسي:** «تحميل الأدوات»

بعد اكتمال جميع فحوص الجاهزية تظهر عبارة «الدخول لـ Termi Ai nexus» بجانب تأثير نجاح واضح، ويصبح الدخول إلى مساحة العمل متاحًا.

التصميم المطلوب: هوية داكنة تقنية أزرق/أسود، حركة وانتقالات سينمائية، خطوط عربية وإنجليزية احترافية، ومساحة واضحة لعرض المراحل والنتائج. جمال الواجهة لا يجوز أن يخفي حالة الخطأ أو يجعل التعليمات الضرورية غير مفهومة.

### 5.2 بوابة الجاهزية

لا يفتح التطبيق مساحة العمل قبل نجاح الشروط التالية:

1. ملف نموذج Aram AI موجود وسليم ومقبول من فحص GGUF.
2. فحص Metadata النموذج يثبت المعمارية المطلوبة وعدد الأوزان، ثم ينجح تحميل النموذج داخل محرك JNI.
3. تشغيل المحرك المحلي وخدمة API بنجاح.
4. Ubuntu/PRoot مثبتان ومهيآن.
5. أدوات Linux المطلوبة موجودة وقابلة للتشغيل.
6. ينجح فحص نهائي من داخل Ubuntu، يتضمن Bash وGit وGitHub CLI وPython والأدوات المحددة في ملف متطلبات الأدوات.
7. ينجح اختبار صحة محرك Aram AI (smoke inference) باستجابة غير فارغة وصالحة، دون اعتبار مجرد وجود ملف GGUF دليلاً على الجاهزية.

**لا يُساوى بين اكتمال تنزيل الملفات واكتمال التثبيت أو التشغيل.**

### 5.3 تسلسل التحميل والتهيئة

تُعرض العمليات في شاشة واحدة، مع تقدم مستقل لكل مرحلة:

1. تنزيل نموذج Aram AI.
2. التحقق من النموذج وسلامة بنية GGUF وبياناته.
3. تحميل النموذج وتشغيل محرك Aram AI.
4. فحص الاستدلال التجريبي والتأكد من جاهزية النموذج.
5. تنزيل Ubuntu Base.
6. التحقق من SHA-256.
7. استخراج Ubuntu وإعداد PRoot.
8. تثبيت أدوات Linux وإظهار الحزم قيد التثبيت والمكتملة والفاشلة.
9. اختبار الأدوات وبيئة النظام.
10. الفحص الشامل ثم إتاحة زر الدخول.

لكل عملية نقل بيانات، يعرض التطبيق المنقول والحجم الإجمالي والمتبقي والنسبة والسرعة والوقت المتبقي فقط عندما تسمح البيانات الفعلية بذلك. مراحل تحميل النموذج في RAM أو استخراج rootfs أو إعداد الحزم تُعرض كمراحل، ولا تُخترع لها نسبة.

### 5.4 شروط الشبكة والتخزين

- قبل التنزيل، يُعرض حجم النموذج وحجم Ubuntu ومتطلبات المساحة المتوقعة وما يتوفر فعليًا.
- لأن ملفات النموذج كبيرة، يجب توضيح استخدام بيانات الهاتف، وإتاحة قرار المستخدم بشأن الشبكة المقاسة قبل بدء النقل.
- لا تبدأ التنزيلات الكبيرة تلقائيًا دون ضغط المستخدم على «تحميل الأدوات» وموافقته على سياسة الشبكة.
- إذا كانت الموارد موجودة وسليمة بالفعل، لا يمنع انقطاع الإنترنت دخول المستخدم.
- إذا فشل اتصال الشبكة والموارد غير مثبتة، يبقى التطبيق في شاشة الإعداد مع Retry واضح وحالة دقيقة.
- إذا أصبح تثبيت سابق غير سليم، يُعرض مسار إصلاح منفصل مع حماية ملفات Linux وبيانات المستخدم.
- تبقى الخدمة مجانية للمستخدم النهائي. لا تُنشأ فوترة تلقائية أو خدمات مدفوعة أو التزام مالي دون موافقة المستخدم.

### 5.5 إزالة أدوات التثبيت المكررة من الواجهات القديمة

بعد نقل الإدارة إلى شاشة الترحيب:

- تُزال أزرار تنزيل/استيراد النموذج وتشغيل تثبيته الأولي من مركز محرك Aram AI القديم.
- تُزال أزرار تثبيت Ubuntu ومسار متابعة تنزيل Ubuntu من شاشة الطرفية القديمة.
- لا تُحذف الخدمات أو APIs اللازمة أو تشخيص الحالة؛ تنقل الواجهات إلى مركز التهيئة المركزي.
- يمكن إبقاء صفحة تقنية متقدمة للعرض والتشخيص والإصلاح المتعمد، لكن لا تبقى مسارات تنزيل متنافسة تتيح بدء عمليات متكررة.
- يجب أن تبقى فحوص الحالة متاحة في الإعدادات، مع زر إصلاح مركزي، دون تجاوز بوابة الجاهزية.

### 5.6 تحديثات وإصلاحات مستقبلية

البوابة ليست شاشة تُعرض مرة واحدة ثم تُنسى. عند بدء التطبيق أو عند طلب المستخدم، تُفحص الجاهزية الفعلية. إذا تغيّر إصدار النموذج أو تلفت أدوات Linux، يفتح مسار تحديث أو إصلاح مناسب مع حفظ النسخة السليمة الحالية حتى نجاح البديل.

## 6. دمج GitHub App بدل Personal Access Token

### 6.1 الوضع الحالي في المستودع

المراجعة أثبتت أن:

- `lib/screens/settings_screen.dart` يطلب GitHub Personal Access Token.
- يُحفظ الرمز تحت `github.token` عبر `SecureVault`.
- `lib/core/github_service.dart` يقرأ PAT ويرسله في Authorization header.
- `lib/screens/github_screen.dart` يعرض المستودعات وينشئ المستودع وIssue وPull Request.
- `terminal_screen.dart` يقرأ الرمز ويمرره إلى `MainActivity.kt`.
- `pty_bridge.c` يضعه في متغيري البيئة `GH_TOKEN` و`GITHUB_TOKEN` داخل shell.

هذه الآلية لا تحقق مواصفة GitHub App المختارة، كما أنها توسع نطاق وصول الطرفية إلى سر GitHub. يجب إزالة PAT كمسار الربط الافتراضي، وإلغاء تمرير الرمز إلى PTY أو shell.

### 6.2 السلوك المعتمد

- طريقة الربط: **GitHub App**.
- الوصول: **المستودعات التي يحددها المستخدم فقط** عند تثبيت GitHub App.
- كل مستخدم يربط حسابه بنفسه؛ لا يوجد رمز مركزي مشترك داخل APK.
- تُمنح أقل صلاحيات ممكنة، وتُفصل صلاحيات القراءة عن الكتابة بحسب عمليات التطبيق.
- يجب أن تكون عمليات إنشاء المستودعات أو التذاكر أو PR أو push أو الحذف خاضعة لبوابات موافقة واضحة.
- تحفظ الرموز على الجهاز باستخدام تخزين آمن يعتمد Android Keystore مع سياسة تدوير وتجديد وإلغاء.

### 6.3 قرار المصادقة الذي يجب حسمه قبل الدمج

توجد طريقتان مختلفتان ولا ينبغي الخلط بينهما:

**أ. User Access Token لتطبيق Android الأصلي:**

- توثيق GitHub يوضح أن User Access Token الخاص بـ GitHub App يقتصر على تقاطع صلاحيات التطبيق وصلاحيات المستخدم، وكذلك الموارد التي يمكن لكليهما الوصول إليها.
- تثبيت GitHub App على مستودعات مختارة يضع حدود الوصول على مستوى التثبيت.
- يمكن طلب `repository_id` لتضييق رمز المستخدم إلى مستودع واحد إضافي عندما يلزم.
- يوضح توثيق GitHub أن User Access Token المنتهي افتراضيًا صالح 8 ساعات، وأن refresh token يمكن أن يعاد به إصدار رمز جديد، وصلاحيته الافتراضية 6 أشهر عند تفعيل الرموز المنتهية/`offline_access`.
- في تدفق Authorization Code، يوصى باستخدام PKCE. لكن استبدال code برمز يتطلب `client_secret` حسب توثيق GitHub. تطبيق Android العام لا يستطيع حماية سر ثابت داخل APK؛ يمكن استخدام خدمة تبادل آمنة صغيرة تحتفظ بالـ client secret ثم تعيد رمز المستخدم الخاص به.

**ب. Installation Access Token:**

- يتطلب JWT موقعًا بمفتاح GitHub App الخاص.
- لا يجوز تضمين private key في APK أو المستودع.
- إن احتاجت عمليات الخلفية إلى رمز تثبيت، فيجب أن يصدر من backend آمن يحتفظ بالمفتاح، ويكون الرمز قصير العمر ومحدودًا بالمستودعات والصلاحيات المطلوبة.
- يذكر GitHub أن Installation Access Token ينتهي بعد ساعة.

**التوصية المبدئية:** لتطبيق Android يستخدم GitHub نيابة عن المستخدم، ابدأ بتقييم User Access Token عبر GitHub App مع Authorization Code + PKCE وخدمة تبادل تحفظ `client_secret` إن كان وجود backend مقبولًا. لا تستخدم Installation Token إلا للمهام التي تحتاج فعلًا هوية التطبيق كـ installation. لا تضع private key في الهاتف. يجب اتخاذ قرار نهائي بشأن الاستضافة وتكلفتها قبل البرمجة؛ لا تُنشأ خدمة مدفوعة أو فوترة دون موافقة.

### 6.4 مركز اتصال GitHub المطلوب

يعرض المركز:

- حالة الربط والحساب والمستودعات التي منحها المستخدم.
- قائمة المستودعات المحددة وصلاحيات كل عملية.
- ربط/فصل الحساب وتجديد التفويض.
- رسالة واضحة عند انتهاء الرمز أو إلغاء المستخدم للصلاحية.
- طلب تأكيد جديد عند الانتقال من القراءة إلى الكتابة.
- سجل عمليات GitHub المهمة دون تسجيل الرمز أو أسرار المصادقة.

يجب ألا يمكن لوكيل أو أمر shell استخدام سر GitHub بمجرد وجوده على الجهاز. يمر GitHub integration عبر خدمة موثوقة ذات API محدد النطاق، وتُفحص كل عملية بناءً على المستودع والصلاحية والموافقة.

## 7. مواصفات المنتج المعتمدة التي يجب الحفاظ عليها

### 7.1 محرك الذكاء الاصطناعي والوكلاء

- يعتمد TermiAI-Nexus على نماذج محلية فقط في بنية تشغيل الوكلاء؛ لا تُحوّل الوكلاء تلقائيًا إلى خدمات سحابية.
- المدير الرئيسي Orchestrator يفهم الطلب ويجهز الخطة ويناقش المستخدم ويشرح القرارات ويعرض البدائل وينتقد القرار عند وجود سبب هندسي واضح وباحترام.
- فريق من الوكلاء المتخصصين، لكل منهم دور وشخصية وأسلوب تواصل مستقل، لكن نشاطه يجب أن يعكس عملًا حقيقيًا لا تمثيلًا.
- لا يبدأ التنفيذ إلا بعد عرض الخطة وموافقة المستخدم.
- لا يُعلن نجاح مهمة دون وجود دليل تنفيذ فعلي.
- يظل التطبيق مجانيًا للمستخدم النهائي، دون فوترة تلقائية.

### 7.2 العالم الافتراضي AETHERIUM

- العالم الافتراضي ثلاثي الأبعاد هو الشاشة الرئيسية بعد اجتياز التهيئة.
- لكل وكيل حضور ومكتب مميز داخل مقر رقمي يشبه المكتب الافتراضي.
- الوكلاء كيانات رقمية ضوئية/تجريدية غير بشرية، وليست صورًا بشرية افتراضية.
- العالم حي بالكامل: يتحرك الوكلاء بين مكاتبهم وقاعة الاجتماعات، وكل حركة مرتبطة بحدث أو مهمة حقيقية.
- عند اختيار وكيل، تنتقل الكاميرا إلى مكتبه وتفتح واجهته التي تعرض معلوماته ومهامه وتتيح التواصل معه.
- الكاميرا تدعم التحريك والتدوير والتقريب والإبعاد، مع وضع اختياري للمتابعة التلقائية للأحداث المهمة.
- يجمع عرض نشاط الفريق بين العالم المرئي ولوحة مراقبة تفصيلية للمهام والحالة والتقدم والأخطاء؛ يجب أن تتطابق المشاهدات مع أحداث التنفيذ الفعلية.
- يجب مراجعة `docs/PRODUCT_SPEC.md`: يذكر أن بعض عناصر المشهد حاليًا ثابتة أو غير متصلة بالأحداث الحية؛ ينبغي عدم الادعاء بأن الحركة الحية اكتملت قبل توصيلها بمحرك الأحداث.

### 7.3 المشروع ومساحة العمل

- يكتب المستخدم طلبه الطبيعي من خانة المساعد في الصفحة الرئيسية.
- يعرض المدير خطة التنفيذ أولًا ثم ينتظر موافقة المستخدم.
- توفر مساحة عمل داخلية في بيئة Linux للمشاريع الجديدة، مع إمكان استيراد الملفات وتصدير المشاريع.
- يمكن ربط مجلدات خارجية من الهاتف باستخدام أذونات Android المناسبة، مع بيان نطاق الوصول وعدم تعديل ملفات خارجية دون إذن.
- يعمل التطبيق في وضع اتصال هجين: المهام المحلية الممكنة تعمل دون إنترنت، والعمليات الشبكية تتأجل وتستأنف بعد عودة الاتصال.
- النسخ الاحتياطي المعتمد للمشاريع عبر GitHub فقط. لا يُلغى ذلك وجود نقاط حفظ محلية مؤقتة لحماية المهمة أثناء التعديل؛ هذه لقطات تشغيلية وليست نظام نسخ احتياطي مستقلًا.
- عند الفشل، يشخّص النظام ويحاول الإصلاح عدة مرات ثم يختبر. إذا فشلت المحاولات، يستعيد تغييرات المهمة فقط ويحافظ على عمل المستخدم والتغييرات غير المرتبطة بها.

### 7.4 واجهة التطبيق واللغة

- واجهات تقنية داكنة بالأزرق والأسود، واضحة واحترافية.
- دعم العربية والإنجليزية مع RTL صحيح للعربية وLTR صحيح للإنجليزية، وبنية تسمح بإضافة لغات مستقبلية.
- شريط تنقل سفلي للأقسام الأساسية وقائمة جانبية للإعدادات والأدوات الإضافية.
- مركز التحكم بطبقتين: إعدادات شائعة بسيطة ولوحة تقنية متقدمة للموارد والخدمات والصلاحيات والمفاتيح وحالة المحرك.
- تقدم تنفيذ المشروع مبسط افتراضيًا، مع لوحة مراقبة عمليات مستقلة للتفاصيل التقنية.
- النصوص الموجهة للمستخدم تحمل بعدًا فلسفيًا ونفسيًا وأدبيًا، مع بقاء التعليمات والأزرار واضحة وغير ملتبسة.

## 10. المخاطر والقرارات التي لا يجوز افتراضها

1. **أداء Spark-X2.6-1.7B على الهاتف:** وجود النموذج داخل APK/التطبيق لا يثبت أنه يعمل بسرعة أو بذاكرة مناسبة على كل جهاز. يجب قياس زمن بدء النموذج وزمن أول token والسرعة والذاكرة وحرارة الجهاز على الهاتف المستهدف.
2. **المهلة الزمنية:** لا يجوز اختيار timeout ثابت صغير يخفي بطء النموذج على حساب قطع المهام الصحيحة. يجب قياس المراحل وتخصيص مهلات منفصلة.
3. **استمرار الخدمة:** Android قد يوقف المهام بحسب إصدار النظام والقيود والبطارية. يجب اختبار lifecycle فعليًا على Android 13+، وخصوصًا القيود الحديثة عند استهداف API 35/36.
4. **استئناف تنزيل Ubuntu:** لا يجوز إعلان دعم resume قبل إثبات توافق المصدر مع Range/ETag والتحقق من سلامة الملف بعد الاستئناف.
5. **تقدم apt:** لا تُعرض نسبة تقدم إلا ببيانات دقيقة؛ وإلا تعرض المرحلة وقائمة الحزم.
6. **GitHub App:** لم يُحسم بعد هل سيُستضاف backend آمن لتبادل OAuth code أو إصدار Installation Tokens. هذا قرار معماري وتشغيلي يجب حسمه قبل ربط المفاتيح.
7. **مفتاح GitHub الخاص:** ممنوع تضمينه داخل APK أو المستودع أو Termux.
8. **PRoot:** يوفر userland ومساحة أسماء، وليس عزلًا أمنيًا صلبًا عن تعليمات Linux الخبيثة. يجب الاستمرار في تطبيق حدود الأدوات والموافقات وعدم وضع أسرار GitHub في بيئة المستخدم.
9. **المشروع المجاني:** يجب تقدير تكاليف أي Backend/خدمة مستضافة قبل اعتمادها، وعدم تفعيل فوترة تلقائية.
10. **الوثائق القديمة:** لا تُستخدم كمصدر حقيقة وحيد قبل تحديثها إلى حالة الفرع الحالية.
11. **الملفات المحلية غير المتتبعة:** لا تلمس `android/aram-source/` أو `tash list` أو أي ملف مستخدم آخر دون فحص وموافقة.

## 11. تعريف الإنجاز النهائي

لا يُعتبر الإصلاح مكتملًا لمجرد نجاح `flutter analyze` أو بناء APK. يعتبر مكتملًا فقط عند تحقق كل ما يلي:

- تغييرات مصدرية في الفرع الرسمي، مع سجل commits واضح ودون فقدان تغييرات المستخدم.
- نجاح تحليل Dart واختبارات Flutter واختبارات Android JVM وبناء APK والتحقق من التوقيع.
- وجود اختبارات lifecycle وpersistence وidempotency وrecovery للمهام.
- تثبيت APK على الهاتف المستهدف واختبار توليد خطة حقيقية مع مغادرة شاشة المساعد والعودة إليها.
- إثبات أن خطة العمل المحفوظة تظهر بعد إعادة فتح التطبيق، وأن موافقة المستخدم مطلوبة قبل التنفيذ.
- اختبار تثبيت Ubuntu كاملًا وأدوات Linux مع إغلاق/إعادة فتح الشاشات، ثم اختبار تعطل العملية واستعادتها.
- إثبات جاهزية نموذج Aram AI عبر inference حقيقي، وليس عبر وجود ملف فقط.
- اختبار GitHub App على حساب تجريبي بمستودعات مختارة، مع إثبات منع الوصول إلى المستودعات الأخرى وعدم تسرب الرمز إلى PTY.
- تحديث وثائق المنتج والحالة لتطابق ما تم التحقق منه، مع فصل الميزات المكتملة عن المؤجلة.
